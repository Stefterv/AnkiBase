# Configuration

## Environment Variables

The installer generates a `.env` file at `/opt/ankibase/backend/.env`. You can edit it manually if needed.

| Variable | Description | Default |
|---|---|---|
| `APP_SECRET_KEY` | Signs media links. Keep it secret | Auto-generated |
| `ANKIWEB_ENCRYPTION_KEY` | Fernet key that encrypts stored API keys | Auto-generated |
| `APP_PORT` | Backend listen port | First free port from `8000` |
| `CORS_ORIGINS` | Other origins allowed to call the API (only for a separately served frontend) | `http://localhost:<port>` |
| `UPDATE_CHANNEL` | `release` (tagged releases) or `main` (every commit) for in-app updates | `release` |
| `GEMINI_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY` | Server-wide AI keys for profiles without their own | – |
| `CUSTOM_AI_BASE_URL`, `CUSTOM_AI_API_KEY` | Server-wide local or OpenAI-compatible AI server (see below); the key only if it needs one | – |

Without the two secrets in `.env`, AnkiBase generates them on first start into `backend/data/.secrets` (mode 0600).
Per-profile data (stories, API keys) lives in `backend/data/<profile>/`.

After editing, restart the service:

```bash
systemctl restart ankibase
```

## Single sign-on (OpenID Connect)

AnkiBase can sign people in with an OpenID Connect provider such as Authentik, Keycloak, Authelia, Zitadel or Google, next to the usual username and password.

1. Register AnkiBase as a client (an "OAuth2/OpenID application") with the provider. Use the authorization code flow, and the redirect URI `https://<your server>/api/auth/oidc/callback`.
2. As an admin, open **Settings → Users → Single sign-on**, fill in the issuer URL, client ID and secret, turn it on and save. Saving checks that the provider can be reached. The client secret is stored encrypted.

You can also set it in `backend/.env` (restart afterwards). These are used until an admin saves the settings in the app; **Use the .env settings instead** there goes back to them.

| Variable | Description | Default |
|---|---|---|
| `OIDC_ISSUER` | The provider's issuer URL (where `/.well-known/openid-configuration` lives) | – |
| `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` | The client's ID and secret (no secret for a public client) | – |
| `OIDC_NAME` | The login button's name: "Sign in with …" | `SSO` |
| `OIDC_SCOPES` | Scopes to ask for | `openid profile email` |
| `OIDC_REDIRECT_URI` | The callback URL, when AnkiBase can't work it out from the request | `<server>/api/auth/oidc/callback` |
| `OIDC_AUTO_CREATE` | Make a user for provider accounts that aren't connected to one yet (“Create users automatically”) | `false` |

The login page then shows **Sign in with …**. Users are matched by their provider account, never by name or e-mail: existing users connect theirs once under **Settings → Account → Connect**, after signing in with their password. With `OIDC_AUTO_CREATE=true`, anyone the provider lets in gets a new user without admin rights. Under **New users study in** you choose what they get: **Their own profile** (a private profile named after them, optionally starting with a fresh copy of another profile's decks: same cards and media, no progress) or **Shared profiles** (access to existing profiles, shared with everyone who has them), so limit who can use the application at the provider.

<Callout type="info">
Single sign-on works in the browser and in the iPhone app. The iPhone app logs in on the server's own website: **Log in** (top right) asks for the server's address and opens its login page in a sign-in sheet, with the password and **Sign in with …** as in the browser, then returns to the app. The provider needs nothing extra (the same redirect URI). The Android app keeps using a username and password for now.
</Callout>

## AI Providers

API keys are managed in the app under **Settings → AI** (or **AI settings** on the Story tab). Each provider has a default model, and you can switch models per story:

| Provider | Default model | Also available |
|---|---|---|
| Anthropic (Claude) | `claude-opus-5-5` | `claude-sonnet-5-5`, `claude-haiku-5-5` |
| OpenAI (ChatGPT) | `gpt-4o-mini` | `gpt-4o`, `gpt-4-turbo`, `gpt-3.5-turbo` |
| Google Gemini | `gemini-2.0-flash` | `gemini-2.0-flash-lite`, `gemini-1.5-flash-8b`, `gemini-1.5-pro` |

AI is optional. Studying, Quizlet, search and stats all work without a key.

### Local models (Ollama, Open WebUI, LM Studio)

Choose **Local / OpenAI-compatible** and enter the server's address. AnkiBase checks that it answers and finds its API path itself, and the model list comes from the server:

| Server | Address to enter | API key |
|---|---|---|
| Ollama | `http://<host>:11434` | none |
| Open WebUI | `http://<host>:3000` | from Settings → Account in Open WebUI |
| LM Studio | `http://<host>:1234` | none |

Anything else with an OpenAI-style `/chat/completions` API works too: enter its base URL, ending in `/v1` or wherever its `/models` lives.

The address must be reachable **from the AnkiBase server**:

- Ollama only listens on `127.0.0.1` by default. If it runs on another machine, start it with `OLLAMA_HOST=0.0.0.0` ([Ollama FAQ](https://docs.ollama.com/faq)).
- With Docker, `localhost` is the AnkiBase container itself. For Ollama on the same machine, use `http://host.docker.internal:11434` (the compose file maps that name to the host) and set `OLLAMA_HOST=0.0.0.0` so Ollama accepts it.

Small models on a CPU can take minutes per story; Reading's word annotations send one request per paragraph.

Keys are saved per profile and encrypted at rest. Who may see or change them is a permission (see below).

## Nginx

The installer can set up nginx automatically. If you need to configure it manually, here's the recommended config:

```nginx
server {
    listen 80;
    server_name your-domain.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name your-domain.com;

    ssl_certificate     /etc/letsencrypt/live/your-domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;

    client_max_body_size 500M;

    location / {
        proxy_pass         http://127.0.0.1:8000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }
}
```

## Users, profiles and permissions

A **profile** is an Anki collection: its own decks, media, review history, sync login, stories
and Quizlet sets. A **user** is someone who logs in. Admins decide which profiles each user can
use; switching profiles (the **Profiles** button) only affects that user's own login.

- The first admin, created by the setup wizard, is the **owner**: only they can change their own
  account, and nobody can delete it. There's always at least one admin.
- Admins can do everything. Members get permissions per user in **Settings → Users**:
  importing decks, using AI, managing AI keys, managing profiles, and changing the default theme.
- Permission changes, removed profiles and deleted users take effect on the next request.
  Changing a password signs that user out everywhere else.

<Callout type="info">
  Profiles are cheap: they all share one Anki engine process, and a collection is only opened when it's used.
</Callout>

## Sync

Each profile has its own sync login, set in **Settings → Sync**: AnkiWeb, or any self-hosted
Anki sync server. Like Anki Desktop, only the sync key is kept (in
`/opt/ankibase/anki-data/anki-cli.json`, readable by root only), never your password.

### Your own sync server

Admins can run **Anki's own sync server** next to AnkiBase (Settings → Sync → Sync server on
this AnkiBase): add an account and it starts, as the `ankibase-sync` service. AnkiBase serves it
at `https://<your AnkiBase>/syncserver/`, so it uses your HTTPS setup and needs no extra port.
Enter that address in Anki Desktop (Preferences → Syncing → self-hosted sync server), AnkiDroid
(Settings → Advanced → custom sync server), AnkiMobile or the AnkiBase iPhone app.
Collections are stored in `/opt/ankibase/anki-data/.sync/data/<account>/`.

Sync modes available:
- **Normal sync** — incremental, merges changes
- **Full upload** — overwrites the server's copy with this one
- **Full download** — overwrites this copy with the server's

## Updates

**Update** in the header (admins) installs the newest tagged release: AnkiBase downloads and
builds it, checks that it starts, backs up your code and data to `/opt/ankibase/backups/`
(the last three are kept), installs it and restarts — and restores the backup if the new
version doesn't come up. `install.sh --update` does the same from the command line.
